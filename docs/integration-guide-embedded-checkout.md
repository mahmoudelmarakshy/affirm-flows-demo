# Embedded Checkout

**Last updated (source doc): Feb 6, 2026**

> **Preliminary — subject to change.** Designs and integration steps in this

> high-level guidance to prospective merchant partners to evaluate
> implementation approaches and estimate engineering effort for Embedded

## Introduction

Embedded Checkout places Affirm's checkout experience directly on the
merchant's site, allowing customers to complete their purchase without ever
leaving the checkout page. By displaying Affirm's UI inline — within the
payment section — shoppers can select a payment plan, confirm their details,
and finalize payment in one continuous flow. This creates a faster, more
seamless experience while still providing the flexibility of multiple
payment options.

This is distinct from Affirm's public **Inline** value-proposition widget
(`affirm.checkout.inline()` / `inline_container`), which surfaces payment
messaging and timelines *before* checkout. Embedded Checkout renders the
**full checkout flow itself** (verify → pick a plan → confirm) inline.

## Integration steps

To use Embedded Checkout, add two new Affirm components to your payment
section:

1. The `affirm-embedded-checkout` element — where AFJS renders the checkout
   **iframe** inline.
2. The `affirm-checkout-confirmation-button` element — a separate,
   merchant-page-native **confirmation button**.

Implementing these components requires loading the Affirm JavaScript library
(`affirm.js`) and placing the two HTML elements within your existing payment
selection UI. Once added, these components render Affirm's checkout
experience inline and let customers confirm payment without leaving the site.

## Technical flow

Upon the Affirm payment method being clicked, the merchant should:

- **Render a defined location** (e.g. `#affirm-embedded-checkout`) for AFJS
  to render the checkout iframe.
- **Render a defined location** (e.g. `#affirm-checkout-confirmation-button`)
  for AFJS to render the checkout button. The button's label and state
  **change dynamically** based on where the shopper is in the Affirm checkout
  flow (e.g. verifying identity → picking a plan → confirming).
- **Call `affirm.checkout.open(...)`.** This is the *same* call used by the
  standard (Direct API) integration — presence of the two DOM containers is
  what causes AFJS to render inline instead of opening a modal or
  redirecting. This call should also be repeated whenever the checkout
  amount changes; doing so reloads the `#affirm-embedded-checkout` element.
- **From there, it's business as usual.** Once `onSuccess` fires (or a
  cancel/redirect signal is received), hand off to your existing
  server-side Authorize flow exactly as with Direct API — Embedded Checkout
  only changes how the front end renders the checkout UI, not the backend
  lifecycle (Authorize / Capture / Void / Refund via the Transactions API).

## Estimated effort

Affirm anticipates this adds ~4 hours of front-end development time on top
of the work needed for a standard Direct Checkout integration.

## How this demo simulates it

This repo's `index.html` models Embedded Checkout as a third flow alongside
Direct API and VCN:

- The front end shows the two mock containers (`#affirm-embedded-checkout`
  rendered inline in the storefront panel, and a separate confirmation
  button whose label changes per step) instead of opening the simulated
  hosted-checkout modal.
- Everything downstream of `onSuccess` — Authorize, the back-office
  Capture/Void/Refund actions — is identical to the Direct API flow, since
  the backend lifecycle doesn't change.
- The "re-call `open()` on amount change reloads the iframe" behavior above
  is called out as an illustrative log note rather than built as live
  interactivity.
